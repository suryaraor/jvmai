Pattern 01 — Java-Native ML

You Don't Always Need Python

Weka has been a Java ML library since 1993 — predates scikit-learn by 20 years. Decision trees, random forests, logistic regression: one Maven dependency, zero external services.

Use when
  • Java-only team — no Python expertise needed
  • Single deployable JAR, no runtime dependencies
  • Classical ML: forests, trees, regressions
  • Compliance requires one fully auditable unit
Skip when
  • Data science team is heavily invested in Python tooling
  • You need deep learning or transformer models

Pattern 02 — ONNX In-JVM

Train in Python. Run in Java. Zero Python at Runtime.

ONNX is the "JAR file for ML models." The Python side exports once. The Java side loads the .onnx file as a Spring bean and calls inference via JNI — no HTTP, no subprocess, no GC pressure from external processes.

Pattern 03 — Model as REST Service

Python Owns the Runtime. Java Owns the Business Logic.

FastAPI Python service. Java calls it. Feature engineering stays in Java — merchant risk tiers, geo risk, velocity logic. Your domain knowledge, in your version-controlled code, in your release pipeline.

Use when
  • Data science team needs to own the model runtime
  • A/B testing model versions without touching Java
  • Custom PyTorch layers ONNX can't export cleanly
  • Model artifacts must live in a separate security zone
Critical resilience patterns
  • .timeout(Duration.ofMillis(500)) — always set one
  • .onErrorReturn(fallbackScore()) — never block on ML
  • Kill Python service → Java keeps processing

Pattern 04 — Spring AI

LLMs as Communicators, Not Decision Makers

Fraud probability 0.93. Great. A fraud analyst still needs to call the customer. A compliance officer needs a written report. "Your fraud probability was 0.93" is not a helpful explanation. That's where LLMs earn their keep.

Provider swap — zero code changes
OpenAI: spring-ai-openai-spring-boot-starter
Claude: spring-ai-anthropic-spring-boot-starter
Ollama (local, no API key): spring-ai-ollama-spring-boot-starter
Same application code. Swap the dependency + one property. Rebuild.
What the LLM returns (typed Java record)
  • Customer-ready message — send verbatim to card holder
  • Risk factors list — bullet points for compliance report
  • Analyst note — escalation summary for risk ops
  • Urgency score 1–10 + recommended action

public record FraudExplanation(
    String summary,
    List<String> riskFactors,
    String recommendedAction,
    String customerMessage,
    String analystNote,
    int urgencyScore
) {}

// Spring AI: reflects on record → generates JSON
// schema → injects into prompt → deserializes response
return chatClient.prompt()
    .user(u -> u.text(PROMPT).params(alert))
    .call()
    .entity(FraudExplanation.class); // ← magic line
Without structured output: you're writing a parser for unstructured text that will break at 2 AM on day three in production. Use .entity().
Pattern 05 — Full Event-Driven Pipeline

Kafka + Docker Compose. Scale to Millions.

Architecture
Payment Gateway
     ↓
[Kafka: "transactions" topic]
     ↓
@KafkaListener → FeatureEngineer
     ↓
FraudScoringService
    ├─ ONNX in-JVM <1ms (primary)
    └─ REST to Python ~50ms (fallback)
     ↓ prob ≥ 0.75
[Kafka: "fraud-alerts" topic]
     ↓
CRM / Risk Ops / Account Freeze
Three-layer fallback — this is what 4-nines looks like
ONNX in-JVM (fast, reliable)
    ↓ fails?
REST to Python (slower, network-dependent)
    ↓ fails?
Safe default 0.0 (pipeline never stops)
Kafka listener — Spring handles all the ceremony
@KafkaListener(topics = "${kafka.topic.transactions}")
public void consume(TransactionEvent event) {
    float[] features = featureEngineer
        .extractFeatures(event);
    double prob = scoringService
        .score(features, event.transactionId());

    if (prob >= 0.75) {
        alertService.raiseAlert(
            event, prob, "HIGH");
    }
}

Which Pattern?

The Decision Matrix

If you need…Reach for
"We only have Java developers" Pattern 1  Weka
"We need sub-millisecond latency" Pattern 2  ONNX
"Data science owns the model runtime" Pattern 3  REST Service
"We need to explain decisions to humans" Pattern 4  Spring AI
"We're processing >10k events per minute" Pattern 5  Kafka Pipeline
"We need maximum production resilience" Pattern 5  + Fallbacks
Patterns Compose

Pattern 5 uses ONNX (P2) as its fast path and REST (P3) as fallback. You might add Spring AI (P4) as a downstream consumer of fraud-alerts to generate human-readable summaries for your risk ops team.

They're not mutually exclusive. Stack the ones your problem needs.

Key Takeaways

Three Things I Wish More Teams Did

01

Keep Feature Engineering in Java

Merchant categories, geographic risk tiers, velocity thresholds — your domain knowledge belongs in version-controlled Java code, reviewed by your team, deployed in your release pipeline. Not in a Python dictionary maintained by a different team in a different repo.

02

Always Have a Fallback

Every ML call in production needs a fallback. A safe default. A cached result. Something. The ML service will have a bad day. Your service shouldn't. Three layers of fallback separates 4-nines services from the ones that don't.

03

Use Structured Output for LLMs

If you're putting an LLM in a production workflow without .entity(YourRecord.class), you're writing a text parser that will break at 2 AM on day three. Spring AI eliminates this entirely. No ObjectMapper gymnastics. Just a typed Java record.
